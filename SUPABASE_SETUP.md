# Vendora × Supabase — backend setup

This project's runtime data layer is Supabase. The MSW handlers in `src/mocks/` are
**test fixtures only** — nothing in the browser falls back to them.

## Decisions this repo runs on

1. **One schema source of truth**: `supabase/migrations/`. The old ad-hoc SQL files are retired to `supabase/_legacy/`.
2. **No silent fallbacks**: `src/lib/supabase.ts` throws at import if `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` are missing (Vitest excepted — it forces the mock layer).
3. **Payments are simulated server-side** inside the `place_order` RPC. No Stripe, no card processor, no client-side price math trusted by the server.
4. **Writes go through RPCs**, reads through RLS-gated views/tables.


## Day-to-day commands

| Command | What it does | Needs a live project |
| --- | --- | --- |
| `npm run db:check` | migrations → seed → RPC/RLS smoke suite, all in PGlite | no |
| `npm run db:seed:gen` | regenerate `supabase/seed.sql` from the mock catalog | no |
| `npm run db:types` | regenerate `src/types/database.ts` from PGlite | no |
| `npm run db:types:remote` | same, introspected from the linked project (authoritative after a push) | yes |
| `npm run db:push` | apply pending migrations to the linked project | yes |
| `npm run db:reset` | **wipe** the linked project, re-apply migrations + `seed.sql` | yes |
| `npm run auth:verify` | read-only live gate: anon sees no rows, each demo persona signs in and reads only its own data | yes |

Docker is not required for any of the offline steps; PGlite stands in for Postgres.

## First-time remote setup (you run these — the password never passes through chat)

```bash
npx supabase login
npx supabase link --project-ref <your-project-ref>
cp .env.example .env        # fill in the project URL + anon key from Settings → API
npm run db:reset            # destructive: drops everything on the remote, then seeds
npm run db:types:remote     # commit the regenerated types alongside the schema
npm run dev
```

`db:reset` seeds identity + catalog + marketing content only. Orders, deliveries and
payouts are created through the RPCs so demo transactions stay internally consistent.

## Demo logins (local development ONLY)

`supabase/seed.sql` creates demo personas for a **local or throwaway** project,
all with the password `demo1234`:

`customer@demo.test` · `newuser@demo.test` · `vendor@demo.test` · `vendor2@demo.test` ·
`admin@demo.test` · `support@demo.test` · `rider@demo.test`

> **Never run the seed against a shared or production project.** These are
> publicly documented credentials — a seeded `admin@demo.test` is a working
> admin backdoor. The production project does not contain these accounts;
> evaluation accounts there use a separate domain and unpublished passwords.

## Staff two-factor authentication (TOTP MFA)

Staff accounts (admin + support) sign in through the staff portal
(`/admin/login`) with a password **and** an authenticator code — Batch 64.
How it works, and what the project owner must know:

- **Dashboard setting**: Supabase Dashboard → **Authentication →
  Multi-Factor** — TOTP is enabled by default on hosted projects; confirm it
  is on. No code or SQL is involved, and nothing else needs configuring.
- **Enrollment is forced, never a lockout**: the first time a staff account
  signs in to the staff portal, it is walked through authenticator setup
  (scan the QR code with Google Authenticator / Microsoft Authenticator /
  Authy, enter the first code) before the console opens. Later sign-ins
  ask for a fresh code. Consoles refuse a password-only (aal1) session, so
  staff signing in through the customer door are bounced to the portal's
  step-up automatically.
- **In-console step-up**: suspending an account, changing a commission
  rate, or issuing a refund asks for a fresh code when the last proof is
  older than 10 minutes.
- **Managing a factor**: Admin Profile → *Password & Sessions* (and Account
  Settings & Security for support staff) shows the factor's status and can
  remove it — removal itself demands a fresh code first.
- **Lost authenticator (recovery)**: there is no code-side backdoor, on
  purpose. The owner resets the factor in the dashboard: **Authentication →
  Users → the staff user → reset/remove the MFA factor**. The account then
  enrols a fresh authenticator at its next staff-portal sign-in, exactly
  like a first sign-in. Keep at least one other admin able to sign in
  before resetting anyone's factor.

## The client

```ts
import { supabase } from '../lib/supabase';          // SupabaseClient<Database> — the only client
```

The typed client in `src/lib/supabase.ts` is the single data-layer entry
point. The untyped legacy clients that existed during the migration were
deleted once every feature moved to typed feature APIs under
`src/features/*/api`.

## Catalog reads

`src/features/catalog/api/products.ts` is the pattern every feature follows: PostgREST
queries with `{ count: 'exact' }` and FK embeds
(`category:categories(...)`, `seller:vendor_profiles(...)`) instead of hand-rolled views,
an `id`-vs-`slug` UUID test for storefront lookups, and a thrown `Error` on any non-empty
`error` — an empty shelf always means the database genuinely returned no rows. Storefront
category/seller filters accept a slug, so the API resolves it to ids first and returns an
empty page when the slug is unknown. Unapproved products never appear: the SELECT policies
hide them, so no `status` filter is added on top (except on listing queries, where it is
the index-friendly predicate).

## Server-side invariants (do not re-implement in the browser)

- **`place_order`**: variant pricing, shipping, coupon consumption, commission, net
  payout, stock decrement, cart clear, hashed delivery code, digital license keys.
- **`advance_sub_order_status`**: legal transitions only, and only by the actor who owns
  that step (customer / vendor / rider / admin); every move is audited.
- **`assign_rider`** (admin) sets `sub_orders.rider_id`; without it no rider can act.
- **`verify_delivery`**: compares against the stored hash — plaintext codes are never persisted.
- **Payouts**: capped at accrued net for the vendor.
- **Moderation**: `products.status` and the rating rollups are frozen for vendors by RLS,
  recomputed by triggers.
- **Rider invites** (Batch 65): the `invite-rider` Edge Function is the only path that
  grants the `rider` role to a new account — it verifies the caller's admin role, sends
  the Supabase invite email, adds `rider` to `profiles.roles` and creates the
  `rider_profiles` row, all with the service role inside the function. Deploy it with
  `supabase functions deploy invite-rider` (see `supabase/functions/README.md` §6,
  including the Auth redirect-URL allowlist entry for `/reset-password`).
